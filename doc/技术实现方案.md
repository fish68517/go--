# 中药房中药材溯源系统新增功能技术实现方案

## 1. 项目现状分析

### 1.1 目录结构

项目根目录主要分为：

- `code/go`：后台主系统，Go + Gin + Gorm + MySQL，包含管理后台页面、业务接口、库存、处方、扫码流转、溯源和区块链上链逻辑。
- `code/vue`：独立 Vue 3 + Vite 溯源查询前端，当前通过 Vite 代理访问 `http://116.198.196.57:9000/queryRecipes`。
- `doc`：项目文档目录。

`code/go` 的核心分层如下：

- `internal/handler`：控制器层，负责路由请求、模板渲染、接口响应。
- `internal/service`：业务服务层，负责组织业务流程。
- `internal/dao`：数据访问层，负责 Gorm 数据库操作。
- `internal/model`：数据库模型。
- `internal/dto`：请求和响应 DTO。
- `internal/routers/router.go`：系统路由。
- `views/includes`：后台 Layui 模板页面。
- `static/admin/module`：后台列表页 JS。
- `configs/dev/config.yaml`、`configs/prd/config.yaml`：包含 `UpChain` 和 `DownChain` 区块链接口地址。

当前 `go.mod` 中声明的是 `go 1.24`，本次实现时需要按要求调整为 `go 1.26.1`，并在本地用对应版本验证编译。

### 1.2 现有业务逻辑

处方主流程：

1. 后台页面 `/prescription/add` 新增处方。
2. `handler/prescription.go` 接收 `dto.PrescriptionDTO`。
3. `dao/prescription_dao.go` 写入 `prescription` 主表和 `prescription_drug` 明细表。
4. 系统生成 `prescription_audit` 审核记录。
5. 后续通过扫码流程写入审核、调剂、复核、泡药、煎药、包装、发货等表。
6. `wx_prescription_view` 汇总处方全流程，用于查询和上链。

溯源和区块链逻辑：

1. `/prescription_scan/upload_chain/:id` 调用 `WxHandler.UploadChain`。
2. 当前上链数据来自 `wx_prescription_view`，封装为 `dto.TisaneRecord`。
3. 上链地址来自配置 `App.UpChain`，当前为 `http://116.198.196.57:9000/uploadRecipes`。
4. `/trace_chinese_medicine/flow` 当前默认从本地 `wx_prescription_view` 查流程数据，文件里保留了从链上 `queryRecipes` 查询的注释版本。
5. Vue 前端 `code/vue/src/App.vue` 直接查询链上 `queryRecipes`，用于展示溯源时间线。

库存和入库逻辑：

1. `/stock_in/add` 新增入库单。
2. `stock_in` 保存入库主单。
3. `stock_in_items` 保存药材明细，已有字段：药材编号、药材名称、数量、单价、金额、批次、生产日期、有效期、备注。
4. 进货源地目前没有独立字段，部分测试数据把产地写在 `remark` 中，例如“甘肃产”“内蒙古产”，这不利于处方选择和溯源展示。

处方药材价格逻辑：

1. `prescription_drug` 已有 `drug_price` 和 `total_prices` 字段。
2. 新增处方页面当前表格主要录入药材名称、编码、单剂量、贴数、总剂量、脚注。
3. 页面 JS 里已有简单的单行计算逻辑，但字段命名和实际业务含义不清晰，尚未形成可支付的价格明细表。

## 2. 新增需求拆解

### 2.1 药材选择时选择进货源地

目标：

- 新增处方药材时，选择药材后可以选择该药材对应的进货源地。
- 进货源地要随处方药材明细保存。
- 溯源查询和区块链上链数据中展示每味药材的进货源地。

建议把“源地”绑定到入库批次，而不是只绑定药材名称。原因是同一种药材可能有多个批次、多个源地、多个单价，处方中必须明确使用的是哪一批。

### 2.2 处方价格明细表和模拟支付

目标：

- 在处方中生成药材价格明细表。
- 展示每味药材的数量、单价、小计和总金额。
- 提供模拟支付功能，不接入真实支付渠道。
- 支付后保存支付状态、支付单号、支付时间、支付方式。
- 可在详情页和溯源数据中查看支付结果。

## 3. 数据库设计

### 3.1 入库明细增加进货源地

修改表：`stock_in_items`

```sql
ALTER TABLE stock_in_items
  ADD COLUMN purchase_origin varchar(100) DEFAULT NULL COMMENT '进货源地' AFTER product_name,
  ADD COLUMN supplier_name varchar(100) DEFAULT NULL COMMENT '供应商名称' AFTER purchase_origin;
```

说明：

- `purchase_origin` 用于正式保存中药材进货源地。
- `supplier_name` 非强制，但建议增加，后续溯源可以展示供应商。
- 历史数据可从 `remark` 中人工或脚本补录源地，不建议继续把源地写在备注中。

### 3.2 处方药材明细增加源地和批次引用

修改表：`prescription_drug`

```sql
ALTER TABLE prescription_drug
  ADD COLUMN stock_in_item_id int DEFAULT NULL COMMENT '关联入库明细ID' AFTER hospital_id,
  ADD COLUMN purchase_origin varchar(100) DEFAULT NULL COMMENT '进货源地' AFTER stock_in_item_id,
  ADD COLUMN batch_no varchar(50) DEFAULT NULL COMMENT '入库批次号' AFTER purchase_origin;
```

说明：

- `stock_in_item_id` 用来锁定实际选中的入库批次。
- `purchase_origin` 和 `batch_no` 在处方药材表中冗余保存一份，保证处方历史快照稳定，不受后续入库数据修改影响。
- `drug_price` 和 `total_prices` 继续复用现有字段，分别表示单价和药材小计。

### 3.3 新增模拟支付主表

新增表：`prescription_payment`

```sql
CREATE TABLE prescription_payment (
  id int NOT NULL AUTO_INCREMENT,
  prescription_id int NOT NULL COMMENT '处方ID',
  prescription_number varchar(60) NOT NULL COMMENT '处方号',
  total_amount decimal(12,2) NOT NULL DEFAULT 0.00 COMMENT '应付总金额',
  pay_amount decimal(12,2) NOT NULL DEFAULT 0.00 COMMENT '实付金额',
  pay_method varchar(30) DEFAULT NULL COMMENT '模拟支付方式',
  pay_status varchar(20) NOT NULL DEFAULT 'UNPAID' COMMENT '支付状态：UNPAID/PAID/CANCELLED',
  mock_trade_no varchar(64) DEFAULT NULL COMMENT '模拟交易号',
  paid_at datetime DEFAULT NULL COMMENT '支付时间',
  created_at datetime DEFAULT CURRENT_TIMESTAMP,
  updated_at datetime DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_prescription_payment (prescription_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='处方模拟支付记录';
```

说明：

- 一个处方只保留一条支付记录。
- 支付明细直接从 `prescription_drug` 生成，支付时把总金额写入 `prescription_payment`。
- 如后续需要严格财务快照，可再扩展 `prescription_payment_detail`，当前需求不需要真实支付，先保持实现简单。

### 3.4 新增区块链上链日志表

新增表：`blockchain_trace_log`

```sql
CREATE TABLE blockchain_trace_log (
  id int NOT NULL AUTO_INCREMENT,
  prescription_id int NOT NULL COMMENT '处方ID',
  prescription_number varchar(60) NOT NULL COMMENT '处方号',
  payload_hash varchar(64) NOT NULL COMMENT '上链内容SHA256',
  tx_id varchar(128) DEFAULT NULL COMMENT '链上交易ID',
  chain_status varchar(20) NOT NULL DEFAULT 'PENDING' COMMENT 'PENDING/SUCCESS/FAILED',
  error_message varchar(500) DEFAULT NULL,
  created_at datetime DEFAULT CURRENT_TIMESTAMP,
  updated_at datetime DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_prescription_number (prescription_number)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='处方溯源上链日志';
```

说明：

- 当前上链成功只把交易 ID 返回给页面，没有持久化。新增日志表后，可以在溯源页显示交易 ID 和 payload hash。

关键字段：

```go
type StockInItem struct {
    PurchaseOrigin string `gorm:"column:purchase_origin" json:"purchase_origin"`
    SupplierName    string `gorm:"column:supplier_name" json:"supplier_name"`
}

type PrescriptionDrug struct {
    StockInItemID  int     `gorm:"column:stock_in_item_id" json:"stock_in_item_id"`
    PurchaseOrigin string  `gorm:"column:purchase_origin" json:"purchase_origin"`
    BatchNo        string  `gorm:"column:batch_no" json:"batch_no"`
```

### 4.2 药材源地选择接口

新增接口：

```text
GET /prescription/drug_sources?product_id=xxx
```

返回示例：

```json
{
  "code": 0,
  "data": [
    {
      "stock_in_item_id": 52,
      "product_id": "10902",
      "product_name": "甘草",
      "purchase_origin": "甘肃",
      "supplier_name": "测试供应商",
```

后端查询逻辑：

- 从 `stock_in_items` 查询指定 `product_id` 或 `product_name` 的可用批次。
- 返回源地、批次、单价、库存数量。
- 如果库存表后续要严格扣减，应关联 `inventory` 或新增批次库存表；当前项目库存只按药材和仓库汇总，第一阶段先做源地选择和快照保存。

### 4.3 新增处方保存逻辑

修改 `dao.PresCreate`：

1. 接收处方药材明细中的 `stock_in_item_id`。
2. 根据 `stock_in_item_id` 回查 `stock_in_items`。
3. 将 `purchase_origin`、`batch_no`、`unit_price` 快照写入 `prescription_drug`。
4. 根据数量计算 `total_prices`。
5. 处方保存成功后，初始化 `prescription_payment` 为 `UNPAID`。

价格计算建议：

```text
药材小计 = 总剂量或数量 * 单价
处方应付总额 = sum(药材小计)
```

如果业务需要加入加工费，可复用现有 `proess_fee` 和 `hospital_tj_vw` 的思路，在第二阶段把加工费加入总额。

### 4.4 支付明细和模拟支付接口

新增接口：

```text
GET  /prescription/payment/detail?id=处方ID
POST /prescription/payment/mock_pay
```

`GET /prescription/payment/detail` 返回：

```json
{
  "prescription_id": 85,
  "prescription_number": "231",
  "pay_status": "UNPAID",
  "total_amount": 42.00,
  "items": [
    {
      "drug_product_name": "甘草",
      "drug_product_number": "GC001",
      "purchase_origin": "甘肃",
      "batch_no": "2025001",
      "quantity": 2,
      "unit_price": 18.00,
      "amount": 36.00
    }
  ]
}
```

`POST /prescription/payment/mock_pay` 请求：

```json
{
  "prescription_id": 85,
  "pay_method": "WECHAT_MOCK"
}
```

支付处理逻辑：

1. 校验处方存在。
2. 重新汇总 `prescription_drug.total_prices`。
3. 如果已支付，直接返回已支付状态。
4. 生成模拟交易号，例如 `MOCKPAY20260521123000123`。
5. 更新 `prescription_payment`：`pay_status=PAID`、`pay_amount=total_amount`、`paid_at=now`。
6. 返回支付成功结果。

### 4.5 区块链上链 payload 扩展

现有 `dto.TisaneRecord` 只包含处方流程字段。需要扩展为包含药材源地和支付信息。

建议新增结构，避免破坏旧字段：

```go
type TraceMedicineRecord struct {
    HospitalName       string              `json:"hospital_name"`
    PatientName        string              `json:"patient_name"`
    PrescriptionNumber string              `json:"prescription_number"`
    Process            []TraceProcessStep  `json:"process"`
    Medicines          []TraceMedicineItem `json:"medicines"`
    Payment            TracePayment        `json:"payment"`
}

type TraceMedicineItem struct {
    DrugProductNumber string  `json:"drug_product_number"`
    DrugProductName   string  `json:"drug_product_name"`
    PurchaseOrigin    string  `json:"purchase_origin"`
    BatchNo           string  `json:"batch_no"`
    Quantity          float64 `json:"quantity"`
    UnitPrice         float64 `json:"unit_price"`
    TotalPrice        float64 `json:"total_price"`
}
```

上链流程：

1. `UploadChain` 根据处方 ID 查询：
   - `wx_prescription_view`
   - `prescription_drug`
   - `prescription_payment`
2. 组装新的 `TraceMedicineRecord`。
3. 计算 payload 的 SHA256。
4. 调用 `App.UpChain`。
5. 将交易 ID、payload hash、状态写入 `blockchain_trace_log`。

查询流程：

- 后台 `/trace_chinese_medicine/flow` 建议优先使用 `App.DownChain` 查询链上数据。
- 如果链服务不可用，可降级查本地 `wx_prescription_view + prescription_drug + prescription_payment`。
- Vue 前端需要展示药材列表中的 `purchase_origin`、`batch_no` 和支付状态。

### 5.4 大屏展示 dapingzhanshi 对接

老师给的 `dapingzhanshi` 是独立的大屏展示前端项目，当前位于：

```text
code/dapingzhanshi
```

该项目是 Vue 2 + Vue CLI + Vuex + ECharts 4，负责展示中药房监管数据全景图。它不直接查数据库，而是通过 Go 后端大屏接口获取处方统计数据。

Go 后端大屏接口路径如下：

```text
GET /buss/bigscreen/bigScreenData/getLatestScreenData
```

对应代码：

- `code/dapingzhanshi/src/api/http.js`：配置大屏前端请求地址。
- `code/dapingzhanshi/src/api/api.js`：封装 `getBigScreenData`。
- `code/dapingzhanshi/src/store/index.js`：请求后端接口并写入 Vuex。
- `code/dapingzhanshi/src/views/LargeScreen.vue`：大屏主页面，读取 Vuex 数据渲染图表。
- `code/dapingzhanshi/src/components/LoopList.vue`：中间滚动处方列表。
- `internal/routers/router.go`：注册 `/buss/bigscreen/bigScreenData/getLatestScreenData` 路由。
- `internal/handler/big_screen.go`：组装大屏响应 JSON。
- `internal/service/big_screen.go`：转发大屏业务查询。
- `internal/dao/bigscreen.go`：查询大屏统计视图。
- `internal/model/big_screen.go`：定义大屏统计模型。
- `oh-admin.sql`：定义大屏依赖的 MySQL 视图。

大屏前端实际请求配置：

```js
// code/dapingzhanshi/src/api/http.js
http.defaults.baseURL = 'http://127.0.0.1:9090/buss/bigscreen'

// code/dapingzhanshi/src/api/api.js
export const getBigScreenData = param => get('/bigScreenData/getLatestScreenData', param)
```

最终请求地址是：

```text
http://127.0.0.1:9090/buss/bigscreen/bigScreenData/getLatestScreenData
```

所以本地联调时需要先启动 Go 服务，并确保 `configs/dev/config.yaml` 里的端口是 `9090`。如果 Go 服务端口调整，大屏前端的 `http.js` 也要同步改。

大屏接口返回结构是：

```json
{
  "success": true,
  "code": 200,
  "timestamp": 1710000000000,
  "result": {
    "state": {
      "totalData": {},
      "marketData": [],
      "produceData": [],
      "useData": [],
      "customerData": [],
      "saleData": [],
      "mapData": []
    }
  }
}
```

各字段来源如下：

- `totalData`：来自 `prescription_total_screen`，统计当天接方、审核、泡药、煎药、包装、发货数量。
- `marketData`：来自 `vw_prescription_dosage_screen`，统计最近 7 天处方贴数。
- `produceData`：来自 `drug_used_total_screen`，统计药材使用量 Top 10。
- `useData`：来自 `prescription_is_decoction_screen`，统计当天代煎/自煎数量。
- `customerData`：来自 `hospital_prescption_tj_vw`，统计医院处方占比。
- `saleData`：来自 `prescription_do_seven_day_screen` 和 `prescription_finish_seven_day_screen`，统计最近 7 天接方和完成数量。
- `mapData`：来自 `prescription_list_screen`，展示当天处方列表。

大屏前端数据流：

1. `LargeScreen.vue` 的 `created()` 调用 Vuex action：`actionBigScreenData`。
2. `actionBigScreenData` 调用 `getBigScreenData()` 请求后端。
3. 请求成功后，把 `res.result.state` 写入 `state.ajaxData`。
4. `LargeScreen.vue` 监听 `ajaxData`，分别写入 `marketData`、`useData`、`customerData`、`produceData`、`saleData`、`mapData`、`totalData`。
5. 各图表组件从 Vuex 中读取对应数据。
6. 中间处方滚动列表 `LoopList.vue` 读取 `state.mapData`，展示字段包括：
   - `hospital_name`
   - `prescription_number`
   - `patient_name`
   - `decoction_type`
   - `dosage`
   - `drug_count`
   - `current_state`

新建处方显示到大屏的条件：

1. `prescription.do_time` 必须是当天日期。大屏多数视图都使用 `cast(do_time as date) = curdate()` 或当天时间范围过滤。
2. `prescription.current_state` 必须是系统认可的状态，例如 `接方`、`审核`、`泡药`、`煎药`、`包装`、`发货`。
3. 新建处方药材必须写入 `prescription_drug`，否则 `drug_used_total_screen` 和价格统计无法体现。
4. `prescription.drug_count` 建议在创建处方时写入药材味数，即 `len(params.Drug)`，否则大屏处方列表中的药材数量可能为空或为 0。
5. 大屏前端需要定时轮询该接口，例如每 5 秒请求一次；后端当前没有 WebSocket 推送逻辑。

当前 `dapingzhanshi` 的问题：

1. `LargeScreen.vue` 只在 `created()` 中调用一次 `getBigScreen()`，后续不会自动重新请求后端。
2. 页面中的时钟每秒刷新，但时钟刷新不会触发接口刷新。
3. 所以新建处方后，如果不刷新浏览器，大屏可能看不到最新数据。

建议把 `LargeScreen.vue` 改成启动数据轮询：

```js
data() {
  return {
    timeString: null,
    myTime: null,
    dataTimer: null
  }
},
created() {
  this.getBigScreen()
  this.dataTimer = setInterval(() => {
    this.getBigScreen()
  }, 5000)
},
beforeDestroy() {
  clearInterval(this.myTime)
  clearInterval(this.dataTimer)
  this.myTime = null
  this.dataTimer = null
}
```

为了满足“上链测试时新建处方需要显示”，实现时需要在新增处方逻辑中补充：

```go
if params.DoTime == "" {
    prescription.DoTime = time.Now().Format("2006-01-02 15:04:05")
}
prescription.CurrentState = "接方"
prescription.DrugCount = len(params.Drug)
```

如果新建处方后立刻上链，大屏不需要等待上链成功才显示。原因是当前大屏读取的是本地数据库视图，不读取链上数据。推荐逻辑是：

1. 新建处方成功后，大屏通过轮询看到 `接方` 状态的新处方。
2. 点击上链后，`UploadChain` 写入 `blockchain_trace_log`。
3. 如需在大屏展示上链状态，再扩展 `prescription_list_screen`，让它左连接 `blockchain_trace_log`，增加 `chain_status`、`tx_id`、`payload_hash` 字段。

推荐扩展后的大屏处方列表视图：

```sql
CREATE OR REPLACE VIEW prescription_list_screen AS
SELECT
  p.hospital_name,
  CASE WHEN p.Is_decoction = 1 THEN '代煎' ELSE '自煎' END AS decoction_type,
  p.prescription_number,
  p.patient_name,
  p.dosage,
  p.current_state,
  p.drug_count,
  pay.pay_status,
  pay.pay_amount,
  chain.chain_status,
  chain.tx_id
FROM prescription p
LEFT JOIN prescription_payment pay ON pay.prescription_id = p.ID
LEFT JOIN blockchain_trace_log chain ON chain.prescription_id = p.ID
WHERE CAST(p.do_time AS DATE) = CURDATE();
```

如果 `dapingzhanshi` 是独立前端项目，不和 Go 服务同域部署，需要注意：

- 后端已有 `middleware.Cors()`，理论上支持跨域访问。
- 生产环境建议通过 Nginx 把 `/buss` 代理到 Go 服务，避免浏览器跨域和接口地址写死。
- 测试时确认 Go 服务端口，例如 `configs/dev/config.yaml` 中当前是 `9090`。
- `public/index.html` 中 `window._DEMODATA['isDemodata']` 必须保持 `false`，否则大屏只展示假数据，不会请求 Go 后端。

## 7. 风险和注意事项

- 当前项目部分中文注释或文案在命令行中显示为乱码，修改页面时需要直接检查浏览器渲染效果，避免引入新的编码问题。
- 当前库存数量使用字符串字段，`StockInCreate` 中存在字符串相加风险，后续如实现真实扣库存，应先把数量计算改为 decimal。
- 当前 `prescription_drug.prescription_id` 数据库字段是 `varchar(15)`，Go 模型中是 `int`，建议后续统一为 `int`，本次可先兼容现状。
- 当前链服务是外部 HTTP 服务，不在本项目内。实现时需要确认外部接口是否允许新增字段；如果不允许，需要在本项目侧保留本地扩展数据，同时链上只提交兼容字段。
- 模拟支付不涉及真实资金流，不应接入微信、支付宝或银行卡 SDK，只保存模拟交易记录。
- 当前大屏接口没有处理 DAO 查询错误，`big_screen.go` 中直接使用返回对象。如果某个视图不存在或查询失败，可能导致接口空数据或 panic。实现时应补充错误处理和默认空对象。
- 大屏统计依赖 `do_time` 的日期过滤。上链测试新建处方时，如果 `do_time` 为空、格式错误或不是当天，大屏不会显示。
